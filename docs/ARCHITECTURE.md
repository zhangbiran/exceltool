# 架构说明

## 选择

首版使用 Python CLI 和 LibreOffice UNO。LibreOffice 是统一的 `.xls/.xlsx`
读写引擎；Python 负责参数、操作语义、输出安全和验证。

选择原因是纯 Go 生态没有成熟的旧版 `.xls` 写入实现，而当前运行环境已具备
LibreOffice 和 `python3-uno`。代价是存在外部进程依赖，保存时也可能重写文件
内部结构，因此验收采用逻辑级往返验证。

## 模块

- `cli.py`：命令、参数、JSON、退出码。
- `engine.py`：启动隔离 LibreOffice、UNO 连接、工作簿读写与低层操作。
- `operations.py`：查看、单元格、sheet 和行的用户语义。
- `fonts.py`：通过 fontconfig 精确检查请求字体与系统解析字体。
- `editing.py`：临时副本、原子发布和写后验证。
- `patching.py`：Patch v1 严格校验、顺序分派、失败定位和最终状态验证计划。

首版保持少量模块，避免为单一引擎建立复杂插件体系。若未来加入第二种引擎，再
抽象公共接口。

二维 JSON 是命令层的稳定数据边界：空值、数字、布尔、文本和公式由统一编解码
规则转换，不暴露 UNO 的 `CellContentType`。裸 JSON 用于管道，带元数据 JSON
用于审计和多目标查看。公式管道按文本保存，结构复制交由 UNO `copyRange`。
样式元数据只附加到 json-full；文本单元格的字体字号通过整段 text cursor 写入，
避免 LibreOffice 保存已有文本时丢失字符属性。验证按内容脚本选择相关字体槽，
并保留三个字体脚本槽的实际值以展示回退。

## 写入流程

1. 校验输入、目标和输出模式。
2. 在临时目录复制输入文件。
3. 使用独立 LibreOffice 用户配置打开副本。
4. 执行一个明确操作并保存为原格式。
5. 重新打开文件验证目标结果和未修改哨兵。
6. 发布到 `--out`，或原子替换输入文件。备份由调用者在命令外显式决定。

Patch 复用同一写入流程，但第 4 步在一个 workbook 实例上按数组顺序执行多个
操作。操作完成后生成最终验证计划；计划只比较稳定的逻辑契约，不比较
LibreOffice 保存时可能规范化的内部直接样式表示。行操作和 sheet 复制验证最终
内容、公式、有效样式与行高，明确样式和硬样式清除验证目标单元格，sheet 名称及
顺序验证结构。整个 patch 仍只调用一次 `save` 和一次只读重开。

## 故障

- `2` 参数错误。
- `3` 文件或 sheet/range 目标错误。
- `4` 格式或功能不支持。
- `5` LibreOffice 编辑或保存失败。
- `6` 写后验证失败。

错误不触发另一引擎、格式转换或伪成功。
